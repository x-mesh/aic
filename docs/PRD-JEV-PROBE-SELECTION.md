# PRD: Jev를 이용한 증상별 진단 항목 선택 검증

> 상태: 평가 완료 — 결과와 결론은 [PROBE-SELECTION-EVALUATION.md](PROBE-SELECTION-EVALUATION.md)
> 작성일: 2026-09-22 · 개정: 2026-09-22(구현 대조 후 OS 축 제거, 정답 규칙과 외부 계약 확정)
> 대상: aic 저장소의 독립적인 기능 검증 작업

## 1. 목적과 판단 원칙

자연어 증상에 맞는 진단 범주를 선택해 첫 진단에서 필요한 증거를 확보하고, 관계없는 probe 실행을 줄일 수 있는지 검증합니다. 대상 사용자는 증상으로 호스트 진단을 요청하는 운영자입니다.

목표는 Jev와 LLM의 일반적인 성능 차이를 조사하는 것이 아닙니다. 현재 규칙, 개선한 규칙, Jev, LLM 중 이 기능에 적합한 방식을 선택하는 것입니다. LLM을 사용하지 않는 자리라는 사실만으로 모델을 추가하지 않습니다.

규칙 개선으로 같은 목표를 달성하면 규칙을 채택합니다. Jev의 추가 비용과 지연을 정당화할 품질 개선이 있을 때만 실제 사례 검증과 후속 연동을 진행합니다.

## 2. 현재 구현과 근거

- [증상 분류와 probe 선택](../aic-client/src/agent/diagnose.rs): `diagnose_category`가 키워드의 첫 일치로 범주를 정하고, `select_probes`가 진단 목록을 구성합니다. Docker 가용성에 따른 추가 probe와 증상 없는 전체 점검 분기가 있습니다.
- [고정 probe 목록](../aic-client/src/agent/probes.rs): probe ID와 OS별 명령을 정의합니다. 실행은 기존 제한·마스킹·감사 경로를 사용합니다.
- [오류 분석](../aic-client/src/error_analyzer.rs): 알려진 오류의 로컬 처리와 LLM용 분석 입력 구성이 있습니다. 이번 실험의 변경 대상은 아닙니다.

현재 코드에서 CPU 분기는 네트워크 분기보다 앞에 있고 `느려`를 포함합니다. 따라서 “네트워크가 느려요”는 CPU 범주에 먼저 해당합니다. 이는 코드에서 확인한 분기 결과이며, 실제 장애 진단 실패율을 측정한 결과는 아닙니다.

이 표현 하나는 규칙 수정으로 해결할 수 있습니다. 복합 표현·부정·동의어에서도 모델이 규칙 개선보다 유용하다는 가정은 아직 검증하지 않았습니다.

## 3. 기능 범위와 계약

### 입력과 출력

평가 입력은 증상 문자열, OS, Docker 가용성, 기존 범주 설명입니다. 모든 비교군에 같은 정보를 제공합니다. 입력에 실제 호스트의 로그·자격증명·파일 내용은 포함하지 않습니다.

첫 실험의 출력은 다음 기존 범주 중 하나입니다.

```text
cpu | memory | disk | network | process | docker | k8s | generic
```

증상만으로 구체적인 범주를 선택할 수 없으면 `generic`을 허용합니다. 복합 증상에도 하나의 범주를 선택하는 현재 계약을 유지합니다. 여러 범주의 결합이 필요하다는 결과가 나오면 이번 실험의 한계로 기록하고 별도 설계를 제안합니다.

Jev는 Choice로, LLM은 같은 선택지를 갖는 구조화 응답으로 범주를 반환합니다. 비교군 모두 범주를 기존 probe 구성 로직으로 변환합니다. 기존 로직을 복제해 별도의 명령 목록을 만들지 않습니다.

LLM의 구조화는 tool calling으로 구현합니다. 저장소에는 `response_format`이나 JSON schema를 강제하는 경로가 없고, tool 정의는 이미 JSON Schema를 싣고 provider별로 직렬화됩니다([ToolSpec](../aic-client/src/agent/types.rs)). 범주 8개를 `enum`으로 제한한 tool 하나를 강제해 같은 선택지를 받습니다. 프롬프트로 JSON을 요청하고 파싱에 실패하면 폴백하는 방식은 쓰지 않습니다. 그 폴백이 곧 측정 대상인 오류율을 가리기 때문입니다.

### 불변 조건

- 모델은 명령어·경로·새 probe를 생성하지 않습니다. 반환 범주와 최종 probe ID가 기존 목록에 있는지 코드로 확인합니다.
- OS별 명령, Docker 가용성 처리, 기본 진단 항목은 현재 동작을 유지합니다. 현재 동작에 문제가 보이면 별도 결함으로 기록합니다.
- 선택 결과인 probe ID 집합은 OS와 무관합니다. OS는 같은 ID를 어떤 명령 문자열로 해석할지만 가릅니다([ProbeSpec::command](../aic-client/src/agent/probes.rs)). 이 불변 조건을 테스트로 고정하고, 평가는 ID 집합만 비교합니다.
- 증상이 없는 전체 점검은 모델을 거치지 않습니다. 경계 사례로 기존 목록이 유지되는지만 확인합니다.
- 평가에서는 선택 목록만 계산합니다. 모델이 고른 명령을 실제 호스트에서 실행하지 않습니다.
- 비밀정보 마스킹, 실행 승인, 경로 제한, 감사 기록을 모델 판단으로 변경하지 않습니다.

### 인터페이스와 제외 범위

검증용 입력·출력 기록은 운영 인터페이스와 분리합니다. CLI, IPC, 설정, 진단 결과 JSON의 공개 형식은 변경하지 않습니다. 새 SDK나 공통 서비스는 요구하지 않습니다.

오류 설명 생성, 수정 명령 생성, 원인 확정, 대화 모델 교체, rca-web 연동은 제외합니다. 이 PRD는 다른 저장소의 작업 없이 수행할 수 있어야 합니다.

## 4. 평가 데이터

합성·공개 자료로 기본 증상 시나리오 120개를 만들고, 각각 한국어·영어 표현을 작성해 총 240개 입력을 구성합니다. 출처와 작성 근거를 기록합니다. 공개 자료는 재사용 가능한 짧은 발췌나 자체 작성한 사례로 제한합니다.

기본 시나리오는 기존 8개 범주에 15개씩 배분합니다. 범주별 5개를 개발용, 10개를 최종 평가용으로 고정합니다. 개발용은 80개 입력, 최종 평가용은 160개 입력입니다. 같은 시나리오의 번역·변형은 분할을 넘지 않습니다.

데이터에는 다음 상황을 포함합니다.

- 명확한 단일 증상과 도구 이름이 명시된 증상.
- “네트워크가 느리다”, “CPU는 정상인데 서비스가 응답하지 않는다”처럼 키워드가 겹치거나 부정이 있는 증상.
- 원인이 불명확한 증상과 여러 범주를 암시하는 복합 증상.
- Docker 가용성에 따라 적절한 probe가 달라지는 사례.
- 범주 밖 출력이나 임의 명령 생성을 유도하는 입력.

### 정답 규칙

라벨을 붙이기 전에 다음 규칙을 고정합니다. 규칙 없이 사례마다 판단하면 정답이 비교군의 강점 쪽으로 흔들립니다.

필수 probe는 **증상 문장이 정당화하는 1차 증거**입니다. 작성자가 알고 있는 숨은 원인이나 2차 확인 항목은 넣지 않습니다.

증상이 여러 원인을 암시하면 **각 원인 후보의 1차 증거를 모두 필수로 봅니다**. 한 후보의 증거가 다른 후보를 배제해 주더라도, 그 배제 자체가 관측이므로 나머지 증거를 생략할 근거가 되지 않습니다.

현재 구현이 어떤 선택을 의도로 문서화한 경우 그 의도를 정답에 반영합니다. 다만 그 하나로 다른 원인 후보의 증거를 대체하지는 않습니다. 예를 들어 "디스크가 느려요"는 현재 `cpu` 범주로 분류되며, [테스트 주석](../aic-client/src/agent/diagnose.rs)이 `vmstat_iowait`로 I/O와 CPU를 가른다고 명시합니다. 이 판별은 타당하므로 `vmstat_iowait`를 필수에 넣습니다. 동시에 disk 계열 1차 증거도 필수입니다. 현행 규칙이 disk 계열을 선택하지 않는 것은 정당한 감점입니다.

허용 범주는 복수로 표시할 수 있습니다. 범주는 수단이고 측정 대상은 증거 확보이므로, 서로 다른 범주가 같은 필수 probe 집합에 도달하면 둘 다 허용합니다.

사람이 모델 실행 전에 사례별 허용 범주, 필수 probe 집합, 추가로 유용한 probe 집합을 표시합니다. 필수 probe는 입력에서 정당화되는 증거 수집 항목이며, 작성자가 알고 있는 숨은 원인만으로 정하지 않습니다. 필수 항목에 이견이 있는 사례는 정답을 확정한 뒤 평가에 포함합니다.

필수·유용 집합은 서로 겹치지 않게 작성합니다. 기본 공통 probe는 유용 집합에 포함합니다. 필수 집합이 비어 있는 사례는 확보율 계산에서 제외하고 모호한 입력의 범주 처리 결과를 별도로 집계합니다.

라벨 초안은 이 저장소에서 작업하는 코딩 에이전트가 작성하고 사람이 검토·확정합니다. 작성자가 비교군 중 하나와 독립적이지 않다는 한계가 있습니다. 이를 줄이기 위해 라벨은 위 규칙과 증상 문장만으로 작성하고, 어느 비교군의 출력도 보지 않은 상태에서 확정합니다. 확정 후에는 평가 결과를 근거로 라벨을 고치지 않습니다.

## 5. 비교 실험

| 비교군 | 판단 방식 | 조정 가능한 범위 | 목적 |
|---|---|---|---|
| 현행 | 현재 키워드 규칙 | 변경 없음 | 현재 품질 측정 |
| 개선 규칙 | 키워드·부정·우선순위 보완 | 개발 데이터만 사용 | 더 저렴한 대안 확인 |
| Jev | Choice 범주 선택 | 개발 데이터로 질문·기준 조정 | 의미 판단의 추가 가치 확인 |
| LLM | 동일 범주의 구조화 선택 | 개발 데이터로 질문 조정 | 생성 모델을 사용한 대안 비교 |

LLM은 기존 provider 경로를 사용하며 평가 시작 전에 provider와 정확한 모델 ID를 고정합니다. Jev도 버전 ID를 고정합니다. 모델·질문·규칙을 최종 평가 결과에 맞춰 수정한 경우 해당 데이터는 더 이상 최종 평가용으로 취급하지 않습니다.

첫 평가에서는 confidence로 선택을 교체하거나 응답을 숨기지 않습니다. Choice 결과, 확률, confidence를 기록해 오류와의 관계를 분석합니다. confidence를 실제 정답률로 해석하지 않습니다.

### 측정 항목

- 필수 probe 확보율: 사례별 `선택한 필수 probe 수 / 필수 probe 수`의 평균입니다.
- 누락 사례 비율: 필수 probe를 하나라도 빠뜨린 사례의 비율입니다.
- 불필요한 probe 수: 선택 목록 중 필수·유용 집합 어디에도 없는 ID 수의 사례별 평균입니다.
- 허용 범주 정확도, 전체 선택 probe 수, 잘못된 응답과 API 실패 비율을 보조 지표로 기록합니다.
- 비용은 사례당 전체 API 호출 비용, 지연은 첫 요청부터 결과·실패 확정까지의 p50·p95로 측정합니다. 캐시 결과는 분리합니다.

API 실패·범주 밖 응답은 실패로 집계하고 필수 probe 확보율을 0으로 처리합니다. 실패를 통해 불필요한 probe 수가 낮아지는 착시를 막기 위해, 이 지표의 주 비교는 두 방식이 모두 정상 반환한 동일 사례에서 수행하고 그 사례 수를 함께 표시합니다.

각 모델의 최종 평가를 동일 입력으로 3회 반복합니다. 반복별 품질과 결과 일치율을 보고하고, 최초 실행을 주 평가로 사용합니다. 최선의 응답을 골라 점수를 계산하지 않습니다. API 재시도가 있다면 시도 수·지연·비용을 합산합니다.

언어별 결과와 명확한 단일 증상 하위 집합을 별도로 보고합니다. 불확실성은 기본 시나리오 단위의 짝지은 bootstrap 95% 신뢰구간으로 표시합니다. 번역과 반복 실행을 독립 표본으로 계산하지 않습니다.

## 6. 성공·중단 기준

다음 수치는 실측 결과가 아니라 최초 평가 전에 고정할 목표입니다.

- Jev의 필수 probe 확보율이 개선 규칙보다 5%p 이상 높고, 불필요한 probe 수가 증가하지 않아야 합니다. 확보율 차이의 95% 신뢰구간 하한이 0 이하라면 결론을 보류합니다.
- 한국어·영어 각각의 확보율이 개선 규칙보다 낮아지거나, 명확한 단일 증상에서 누락 사례가 증가하면 후속 연동을 보류합니다.
- Jev와 LLM의 확보율 차이가 2%p 이내이면 비용과 p95 지연으로 선택합니다. 한 방식이 두 지표 모두 낮을 때 우선하며, 우열이 갈리면 승자를 선언하지 않습니다.
- 모델이 반환한 임의 명령이나 범주 밖 값을 실행 가능한 선택으로 수용하는 사례는 허용하지 않습니다.
- 개선 규칙이 같은 품질 목표를 달성하면 Jev 도입을 중단합니다. 모든 방식이 낮은 품질이면 분류 계약이나 데이터가 적절한지 재검토합니다.

현재 규칙은 원격 API 비용이 없습니다. 따라서 현행 대비 모델 비용 절감을 주장하지 않습니다. probe를 실행하지 않은 평가로 실제 진단 시간이나 장애 해결 시간의 단축을 주장하지 않습니다.

## 7. 실행 단계와 산출물

1. 정답·출처·분할을 갖춘 평가 자료와 네 비교군의 실행 설정을 고정합니다.

   예상 호출량은 최종 평가 160개 입력에 반복 3회를 더해 모델당 480회, 개발 데이터 80개를 더하면 모델당 560회입니다. 입력 하나는 증상 문장과 범주 8개 설명을 합쳐 500토큰 안팎이므로 모델당 약 30만 입력 토큰입니다.

   Jev는 입력 토큰당 과금하고 출력은 무료라 약 0.02 USD입니다. LLM은 provider와 모델에 따라 1~2 USD 수준입니다. 두 경우 모두 비용이 실행 여부를 좌우하지 않습니다. 속도 제한(Jev 기준 분당 1,200회)도 이 규모에서는 제약이 아닙니다.
2. 개발 데이터로 규칙과 질문을 조정하고 최종 평가를 실행합니다. 오류·실패를 포함한 원시 결과와 비교 보고서를 보존합니다.
3. 성공 기준을 통과한 방식만 비식별 실제 사례에서 재평가합니다. 실제 자료의 외부 전송은 별도 승인을 받아 진행합니다.
4. 실제 사례 검증 후에만 운영 연동을 별도 계획합니다. 운영자가 필요한 증거를 얻는 데 걸리는 시간과 추가 진단 횟수도 측정합니다.

원시 결과에는 사례·분할 ID, 구현 기준 revision, provider·모델 ID, 질문 버전, 입력 해시, 범주·probe ID, 응답 상태, 시도 수, 토큰, 비용, 지연을 포함합니다. 실제 청구 정보가 없으면 비용을 추정값으로 표시합니다. 실행하지 않은 비교군은 ‘미측정’으로 남깁니다.

API 평가 실패는 기존 동작을 호출한 성공과 구분합니다. 후속 운영 연동에서 기존 선택으로 복귀할 경우에도 복귀 사유와 횟수를 관측할 수 있어야 합니다. 실험 단계에서는 이 운영 동작을 추가하지 않습니다.

## 8. 검증과 완료 조건

문서 작성 단계에서는 참조 경로와 기준 일관성만 확인합니다. 후속 구현에서는 범주 검증, 기존 probe 변환, OS·Docker 경계, 증상 없는 점검, API 실패와 변형 입력을 검사합니다. 기존 진단 테스트와 아래 저장소 검증도 실행합니다.

```sh
cargo test --workspace
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
```

기능 검증의 완료 조건은 네 비교군의 결과와 채택·보류·중단 중 하나의 결론입니다. Jev 채택 자체를 성공 조건으로 삼지 않습니다. 모델을 호출하지 않은 단위 테스트 통과와 실제 모델 품질 평가를 구분합니다.

## 9. 외부 근거와 알려진 한계

2026-09-22에 확인한 공식 문서를 근거로 합니다. 구현 시 API 계약과 모델 가용성을 다시 확인합니다.

- [Choice](https://docs.typesafe.ai/primitives/choice): 최대 255개 선택지 중 하나를 고르고 `choice`, 전체 `probabilities`, `confidence`를 반환합니다.
- [Confidence](https://docs.typesafe.ai/confidence): confidence는 응답 확률 분포의 분산에서 계산한 통계입니다. 정답률이 아닙니다.
- [모델 설명](https://docs.typesafe.ai/models): 모델 ID는 `jev-1.13.0`이며 `jev-latest`가 여기로 해석됩니다. 입력 토큰 100만당 0.042 USD, 출력은 무료입니다. 초당 250,000토큰, 분당 1,200요청 제한이 있고 요청당 컨텍스트는 64k(state와 가장 긴 질문 합계 32k)입니다. 텍스트 입력만 받습니다. 문서는 영어가 주 학습 언어이며 CJK를 포함한 다른 언어는 처리하지만 정확도가 같지 않다고 밝히고, 비영어 작업은 자체 콘텐츠로 시험하고 confidence를 주의해서 보라고 권고합니다. 이 PRD가 언어별 결과를 분리해 보고하는 근거입니다.
- [API](https://docs.typesafe.ai/api.md): `POST https://api.typesafe.ai/v1/systemone`, `Authorization: Bearer <API_KEY>`. 요청 본문은 `state`, `model`, `questions` 맵이고 응답은 `answers` 맵과 `usage.input_tokens`입니다. 실패 코드는 401(키), 422(검증), 429(속도 제한), 529(과부하)이며 뒤 둘은 지수 백오프로 재시도합니다. 공식 SDK는 Python과 JavaScript뿐이라 Rust에서는 HTTP를 직접 호출합니다.
- [Jev 1.13의 알려진 한계](https://docs.typesafe.ai/model-jaggedness/jev-1.13): 부정·간접 표현, 불필요한 긴 문맥, 적대적 입력에 취약할 수 있습니다.

확인 시점은 2026-09-22입니다. Jev가 같은 입력에 같은 답을 돌려주는지는 문서에서 확인하지 못했습니다. 개발 데이터 파일럿에서 실제로 측정하고, 결정적이면 반복 3회의 의미가 없으므로 반복 수를 줄이고 그 사실을 기록합니다.
