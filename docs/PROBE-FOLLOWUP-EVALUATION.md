# Probe Follow-up Selection Evaluation

> `aic diagnose`가 1차 probe 증거를 본 뒤 고르는 follow-up probe(예: `journal_unit nginx.service`)를
> TypeSafe Jev의 Choice로 고를 수 있는지 잰 결과. 실행 상세와 원시 수치는 `eval/RESULTS.md`의
> "Jev follow-up 선택 평가" 절.
> 작성일: 2026-09-22 · 상태: production 반영 완료(v0.49.0) · 결론: 모델 없이 결정적 규칙으로 간다

## 무엇을 쟀나

`aic diagnose`는 1차 probe 출력을 LLM에 넘기고, LLM은 분석과 함께 follow-up 블록에 최대 3줄을
쓴다. 메뉴는 catalog 59개와 인자형 템플릿 10개(`journal_unit <unit>`, `proc_fd <pid>`,
`docker_logs <container>`, `k8s_pod_describe <pod>` 등)다. `resolve_followup_line`이 각 줄을
게이트한다: 인자는 evidence 안에 토큰 단위로 등장해야 하고 문자 집합과 길이 제한을 지켜야 한다.

이 단계가 Jev에 맞는다고 본 이유는 세 가지다. 선택지가 닫혀 있다(70개 메뉴 + `none`). 인자
후보를 evidence에서 결정적으로 뽑을 수 있다(`failed_units` 표의 유닛명, `proc_fd_top` 표의 PID,
`docker ps`의 NAMES 열, `kubectl get pods`의 NAME 열). 정답이 구성상 정해진다 — 신호 섹션이
대상을 드러내고, 그 대상을 더 깊이 보는 템플릿이 정답이다.

Jev 비교군은 두 질문을 한 요청에 묶는다: Q1 템플릿 Choice(catalog 59 + 템플릿 10 + `none`),
Q2 템플릿별 인자 Choice(evidence에서 뽑은 후보 + `__none__`). LLM 비교군은 production
프롬프트(`build_diagnose_prompt_followup`)를 `kiro/gpt-5.6-luna`로 그대로 돌려 follow-up 블록을
추출하고 같은 게이트를 통과시킨다.

데이터는 26개 번들(개발 10, 최종 16)이다. 신호 섹션은 probe-judgment fixture와 새로 쓴
docker/k8s 표에서, 잡음 섹션은 판정이 none인 clean-negative fixture에서 가져왔다. 실제 호스트
출력은 섞지 않았다.

## 결과

최종 분할 16 번들(신호 12, 신호 없음 4), 3회 반복, 주 평가는 1회차.

| 지표 | Jev | LLM(luna) |
|---|---|---|
| top-1 정답(신호 12) | **0.833** (10/12) | 0.333 (4/12) |
| top-3 정답(신호 12) | 1.000 | 0.750 |
| none 정답(신호 없음 4) | 0.500 (2/4) | 0.000 (0/4) |
| 게이트 거부 | 0 | 0 |
| 반복 일치율(16 번들 × 3회) | **0.938** | 0.438 |
| p50 / p95 지연 | 246 / 332 ms | 10,052 / 14,090 ms |
| 입력 토큰(1회차 16회 합) | 52,719 (호출당 ≈ 3,300, ≈ 0.0022 USD) | 미측정 |

개발 분할 10 번들에서는 Jev top-1 8/8·none 2/2, LLM 3/8·0/2였다. 두 분할을 합치면 Jev
18/20·4/6, LLM 7/20·0/6이다.

LLM 지연이 10초인 이유는 production 프롬프트가 분석 전문을 쓴 뒤 follow-up 블록을 붙이기
때문이다. Jev는 follow-up만 고른다. 같은 조건은 아니지만, production에서 follow-up이 나오기까지
걸리는 시간은 이 값이다.

## LLM이 약한 이유

LLM 오답 8건 중 6건은 인자형 템플릿 대신 catalog probe를 골랐다: `proc_fd 73006` 대신
`fd`(4건), `journal_unit a.service` 대신 `journal_errors`(2건), `k8s_pod_describe ingest-5d2a-q9`
대신 `k8s_crashloop_pods`. 대상이 표에 그대로 있는데도 넓은 probe로 되돌아간다. 신호 없는
4건에서는 매번 다른 probe(`proc_changes`, `vmstat_iowait`, `memory`, `uptime`)를 골랐고 `none`을
쓴 적이 없다. 반복 일치율 0.438은 같은 evidence에 세 번 중 두 번은 다른 follow-up을 낸다는
뜻이다.

production의 follow-up 단계는 지금 이 상태로 동작한다.

## Jev가 틀린 4건 — 전부 `proc_fd`

| 번들 | 정답 | Jev(1회차) | confidence | 표의 행 |
|---|---|---|---|---|
| nn-05 | none | `proc_fd 904` (3/3회) | 0.65 | `50 904 tiny`, 한도 100000 |
| nn-06 | none | `proc_fd 904` (3/3회) | 0.49 | 같은 행 |
| dk-04 | docker_* api-2 | `proc_fd 905` (3/3회) | 0.69 | `900 905 mid2`, 한도 줄 없음 |
| pf-08 | proc_fd 103 | `proc_fd 905` (1회), `proc_fd 100` (2·3회) | 0.86 | 같은 행 + 한도 5000 표 |

네 건 모두 `proc_fd_top` 표의 행을 대상으로 골랐고, 스캐너(`scan_proc_fd`) 기준으로 그 행은
신호가 아니다: 50/100000은 0.05%이고, 한도 줄이 없는 900은 절대량 경고선(10,000)에 못
미친다. `proc_fd_top` 표가 없는 12 번들은 전부 맞혔고, 표가 있는 14 번들 중 4건이 틀렸다.

다만 표가 있다고 무조건 틀리지는 않았다. 같은 `900 905 mid2`나 `50 904 tiny` 행이 잡음으로 든
fu-02·fu-03·pf-05는 맞혔다. 증상이 유닛을 가리키거나(`서비스가 죽었습니다`) 진짜 90% 행이 같이
있으면 그쪽을 골랐다. 틀린 경우는 두 가지다. 증상이 없고 다른 신호도 없으면 `none` 대신 표에
있는 아무 행을 고른다(nn-05·nn-06). 한도 없는 `900`을 크다고 보고 컨테이너 증상(dk-04)이나 80%
행(pf-08 1회차)보다 앞세운다. 두 번째는 판정 실험에서 확인한 것과 같은 약점이다: Jev는 수치를
한도와 견줘 판단하지 못한다.

confidence로는 못 거른다. 정답 46건의 confidence는 0.39 이상(중앙값 0.86), 오답 12건은
0.46~0.89로 겹친다.

## 데이터 결함(실측 후 발견, 고치지 않음)

최종 분할의 실패를 읽었으므로 이 분할은 질문 조정에 다시 쓰지 않는다. 결함은 다음 라운드용으로
기록만 한다.

- 생성기 `noise(k, signal_sections and "" or "")`가 제외 probe에 항상 빈 문자열을 넘긴다. 잡음
  풀에서 신호 probe를 빼지 못해 pf-05는 `proc_fd_top` 표 2개, pf-08은 3개를 품었고, 신호 없는
  nn-05·nn-06에 `proc_fd_top` 정상 행이 들어갔다. 후자는 Jev의 약점을 드러냈으니 결과적으로 쓸모
  있었지만 의도한 설계는 아니다.
- dk-04 정답이 evidence와 어긋난다. `replace("Up 5 days", …, 1)`이 `db-1`이 아니라 `worker-3`
  행을 바꿨는데 정답은 `db-1`을 적었고, dk-02·dk-03과 달리 `docker_health`·`docker_logs_since`를
  뺐다. 일관된 정답이면 LLM의 `docker_logs_since api-2`는 정답이라 LLM top-1은 5/12(0.417)가
  된다. Jev는 어느 정답으로도 오답이다.
- pf-08 정답이 "fd 열이 가장 큰 PID"(103) 하나뿐이다. 스캐너는 한도의 50% 이상을 표 순서로 최대
  3개까지 보고하므로 실제 출력은 100·101·102이고 103은 나오지도 않는다. Jev 2·3회차의
  `proc_fd 100`은 스캐너 기준 정답이다.

정답을 고쳐도 Jev 1회차 top-1은 10/12로 같고, 2·3회차는 11/12가 된다.

## 배운 것

- **follow-up 선택은 지금까지 시험한 세 단계 중 Jev에 가장 잘 맞는다.** 증상→범주(1단계)는
  규칙이 Jev와 같은 품질에 닿았고, probe 판정(2단계)은 수치 비교에서 실패했다. follow-up은
  선택지가 닫혀 있고 인자 후보가 결정적으로 뽑히며 정답이 범주형(실패 유닛, 죽은 컨테이너, 못
  뜨는 파드)이다. 이 조건에서 Jev는 LLM보다 top-1 정답이 2.5배, 반복 일치율이 2배 높았고 지연은
  40분의 1이었다.
- **약점은 2단계와 같은 곳에서 나온다.** 수치를 한도와 견주는 판단은 Jev가 아니라 스캐너
  몫이다. `proc_fd` 후보를 `scan_proc_fd`가 실제로 경고한 PID로 제한하면 네 건 모두 구성상
  사라진다. 후보가 없으면 `proc_fd` 템플릿 자체를 메뉴에서 뺀다. 결정적 스캐너가 후보를 좁히고
  Jev가 그 안에서 고르는 구조는 1단계의 "규칙이 조절하고 모델이 고른다"와 같다.
- **정답 키는 생성기 코드가 아니라 스캐너 출력으로 만들어야 한다.** pf-08과 dk-04 결함은 둘 다
  정답을 손으로 정한 데서 왔다. `scan_findings`가 뽑는 대상을 정답으로 삼으면 스캐너와 어긋날 수
  없다.
- **LLM이 인자형 템플릿을 쓰지 않는다는 사실은 production 결함이다.** Jev 도입과 별개로,
  프롬프트가 템플릿 사용을 유도하지 못하거나 LLM이 넓은 probe를 선호한다. 원인은 확인하지
  않았다.

## 남은 제한

- 최종 n=16은 작다. docker 3, k8s 1 번들뿐이고 `k8s_nodes`·`k8s_node_describe` 같은 템플릿은
  시험하지 못했다. 신뢰구간을 계산하지 않았다.
- 정답이 구성상 정해진 합성 번들이다. 실제 `aic diagnose` evidence는 섹션이 더 많고 길며, 기존
  redaction이 호스트명·경로·저널 본문을 남긴다. Jev 64k 문맥 한도와 전송 정책을 실제 evidence로
  확인하지 않았다.
- LLM 토큰은 `send()` 경로가 사용량을 기록하지 않아 재지 못했다.
- Jev 비교군은 follow-up만 고르고 LLM 비교군은 분석까지 쓴다. 지연 차이의 일부는 이 차이다.

## 다음 단계

1. 생성기 수정: 제외 probe 인자, dk-04·pf-08 정답, 정답을 스캐너 출력에서 생성. 최종 분할을 새로
   뽑는다(현재 최종 분할은 소진).
2. `proc_fd` 후보를 스캐너 경고 PID로 제한하고 후보 없는 템플릿을 메뉴에서 제외한 뒤 개발 분할로
   재확인.
3. n을 50 이상으로, docker·k8s 번들을 늘려 최종 재측정. 진행 문턱은 실측 전에 고정한다: top-1
   ≥ 0.85, none 정답 ≥ 0.90, 반복 일치율 ≥ 0.90.
4. 통과하면 production 배선 설계: 1차 evidence → Jev follow-up 선택 → follow-up 실행 → LLM 분석
   한 번. follow-up이 LLM 분석 앞으로 옮겨져 지연이 줄고, 실제 evidence 길이와 redaction 범위를 이
   시점에 확인한다.

# 2라운드 — 후보를 좁힌 뒤

1라운드의 Jev 오답 4건은 전부 `proc_fd_top` 표의 정상 행을 대상으로 고른 것이었다. 수치를 한도와
견주는 판단은 모델이 아니라 스캐너의 몫이므로, 후보 자체를 **문제가 드러난 행**으로 좁히고 다시
쟀다. 함께 규칙 비교군을 넣어 "후보를 좁힌 뒤에도 모델이 필요한가"를 물었다.

## 무엇을 바꿨나

- `proc_fd` 후보는 `scan_proc_fd`가 경고한 PID만(한도의 50% 이상 또는 절대 10,000개 이상, 표 순서
  최대 3개). 이를 위해 `diagnose.rs`에 `scanned_proc_fd_pids`를 공개했다 — 임계 판단의 출처는 계속
  한 곳이다.
- docker는 STATUS가 `Up`이 아니거나 `(unhealthy)`·`(Paused)`인 행만, k8s pod는 `Running`/`Completed`/
  `Succeeded`가 아닌 행만(로그는 컨테이너가 한 번이라도 뜬 `CrashLoopBackOff`·`Error`·`OOMKilled`만),
  노드는 `NotReady`·`Unknown`만.
- 후보가 없는 템플릿은 Jev 메뉴에서 뺀다(질문 `v3`). catalog probe 59개는 그대로 올린다.
- 번들을 62개(개발 24 / 최종 38)로 늘리고 섹션 형식을 실제 명령 출력에 맞췄다. 1라운드의 표는
  실제와 달랐다: `docker_ps`는 `docker ps -s`라 NAMES 뒤에 SIZE 열이 있고(마지막 토큰이 이름이
  아니다) `-a`가 없어 종료된 컨테이너는 나오지 않으며, `k8s_pods_notready`는 `grep -v Running`을
  거치므로 표에 남는 정상 행은 끝난 Job뿐이다. 후보 추출을 헤더 오프셋 기준으로 다시 썼다.
- 정답 집합이 결정적 후보 집합과 **같아야** 한다는 규칙을 `followup-validate`가 강제한다. 1라운드의
  dk-04·pf-08 정답 결함은 정답을 손으로 정한 데서 왔다.
- 규칙 비교군(`rules`)을 더했다: 고정 우선순위(`journal_unit` → `proc_fd` → `docker_logs` →
  `k8s_pod_describe` → `k8s_node_describe`)로 첫 후보를 고른다. 네트워크가 없다.

개발 24 번들에서는 규칙 24/24, Jev 신호 19/19 · none 4/5였다. 반복 3회에서 Jev는 매회 top-1

**규칙의 1.000은 성과가 아니라 구성이다.** 정답 집합을 결정적 후보 집합과 같게 정의했으므로 그
후보의 첫 항목을 고르는 비교군은 틀릴 수 없다. 이 라운드는 "모델이 규칙보다 나은가"에 답하지
못한다 — 그 답은 사람이 정답을 매긴 데이터가 있어야 나온다. 여기서 알 수 있는 것은 아래 세 가지다.

## Jev가 틀린 5 번들 — 두 가지 실패 유형

세 번 반복에서 모두 같은 사례를 틀렸다.

**(A) 템플릿은 맞히고 인자를 "대상 없음"으로 답한다 — fu-05, kn-03 (실패 2건)**

| 번들 | 후보 | 템플릿 confidence | 인자 답 | 인자 confidence |
|---|---|---|---|---|
| fu-05 | `journal_unit` f~l.service 7개 | 0.93~0.95 | `__none__` | 0.46~0.53 |
| kn-03 | `k8s_node_describe` gke-prod-pool-1-{7f2a,9c1b} | 0.96~0.97 | `__none__` | 0.32~0.33 |

둘 다 후보 이름이 서로 닮은 다중 대상이다. Jev는 "이 템플릿을 돌려야 한다"는 것은 0.95로 확신하면서
"어느 대상인지는 이 중에 없다"고 답했다. 후보는 전부 정답이므로 무엇을 골라도 맞는 자리였다.

**(B) 신호가 없을 때 `none` 대신 넓은 probe를 하나 더 고른다 — nn-09, nn-14 (+ dk-05)**

- nn-09(증상 없음, 정상 `Completed` pod만): `k8s_events_warning` / `k8s_pods_notready`, confidence 0.29~0.30
- nn-14(증상 없음, 정상 `proc_fd_top` 행만): `proc_fd_top`, confidence 0.39~0.52
- dk-05(`Up 3 days (Paused)` 컨테이너): `none`, confidence 0.41~0.44 — 이쪽은 반대 방향이다. 멈춘
  컨테이너를 문제로 보지 않았다. 우리 필터는 문제로 센다.

(B)의 선택은 전부 인자 없는 catalog probe다. 운영에서 보면 "읽기 전용 probe를 하나 더 돌린다"라
해가 적지만, 정답 기준으로는 오답이다.

## confidence가 두 실패를 모두 가른다

개발·최종 합쳐 Jev 138건 기준이다.

| 신호 | 정답 | 오답 |
|---|---|---|
| 템플릿 confidence | n=122, 중앙값 0.83, 하위 10% 0.42 | 의미 오답 10건 **0.29~0.50** / 인자 실패 6건 0.93~0.96 |
| 인자 confidence | n=97, 중앙값 0.99 | `__none__` 6건 **0.32~0.53** |

두 신호가 서로 다른 실패를 잡는다. 템플릿 confidence < 0.55는 (B) 유형 10건을 전부 걸러내고,
인자 답이 `__none__`인 것은 (A) 유형 6건을 전부 걸러낸다. 둘을 합치면 오답 16건이 모두 걸러지며
폴백은 138건 중 33건(24%)이다. 이 데이터에서는 폴백 대상이 규칙으로 전부 맞으므로 폴백 비용이
0이지만, 그것은 규칙이 구성상 100%이기 때문이다.

## 현행 production(LLM)의 약점은 1라운드와 같다

LLM 오답 10건 중 6건은 대상이 표에 있는데도 넓은 catalog probe로 되돌아갔다(`fd` 4건,
`journal_errors`, `k8s_events_warning`). 신호 없는 9건에서는 8건이 무언가를 골랐고, 그중 4건은
정상 행을 대상으로 한 인자형 follow-up이었다(`docker_inspect_container worker-3`,
`k8s_node_describe node-b` 등) — 1라운드에서 Jev가 저질렀고 이번에 후보 필터로 막은 바로 그
오답이다. 반복 일치율 0.526은 같은 증거에 두 번 중 한 번은 다른 follow-up이 나온다는 뜻이다.

**비교의 공정성**: Jev와 규칙은 좁힌 후보를 받고, LLM은 production 프롬프트의 69개 메뉴를 그대로
받는다. 이 표는 모델끼리의 비교가 아니라 "후보를 좁힌 시스템 대 현행 production"이다. LLM에 같은
후보를 주면 결과가 달라질 수 있으며, 그것은 재지 않았다.

## 사전 문턱 판정

| 기준(실측 전 고정) | Jev 실측 | 판정 |
|---|---|---|
| top-1 ≥ 0.85 | 0.897 | 통과 |
| none 정답 ≥ 0.90 | 0.778 | **미달** |
| 반복 일치율 ≥ 0.90 | 0.974 | 통과 |

`__none__` 폴백(인자 답이 `__none__`이면 첫 후보)을 넣으면 top-1은 0.966(28/29)이 되지만 none 정답은
그대로다. 신호 없는 증거에서 `none`을 고르는 것이 Jev의 남은 약점이고, 그것은 임계 판단과 같은
성격의 문제다.

## 결론: 모델을 쓰지 않는다

follow-up 선택에서 판단이 필요한 부분은 **어느 행이 문제인가**이고, 그것은 이미 결정적 스캐너와
STATUS 필터가 안다. 그 뒤에 남는 "어느 템플릿을 먼저 돌릴까"는 우선순위 한 줄로 충분하며, Jev는
거기서 0.897/0.778을 냈고 규칙은 구성상 1.000이다. 증상→범주(1단계)에서 규칙 어휘를 보강하니
모델과의 차이가 사라졌던 것과 같은 결론이다.

Jev가 유일하게 더 줄 수 있는 것은 **여러 대상 중 어느 것을 먼저 볼까**의 순서다(fu-09에서 Jev는
`etcd.service`, 규칙은 표 순서대로 `logrotate.timer`를 골랐다 — 둘 다 정답 집합 안이지만 운영자에게
유용한 쪽은 etcd다). 그 가치를 재려면 "정답 하나"가 아니라 사람이 매긴 우선순위가 있는 데이터가
필요하다. 지금은 없다.

## production에 넣을 것

`scan_findings`의 `Finding.suggested_followup`은 현재 `failed_units`에만 붙는다(`journal_unit <unit>`).
이번에 검증한 필터를 그대로 옮기면 `proc_fd_top`·`docker_ps`·`k8s_pods_notready`·`k8s_nodes`에도
붙는다. 그러면 follow-up이 LLM 분석을 기다리지 않고 나오고(현재 p50 10.9초), 같은 증거에 항상 같은
값이 나온다(현재 반복 일치율 0.526). LLM의 follow-up 블록은 그대로 두되, 결정적 제안이 있으면 그것을
앞에 놓는다.

## 남은 제한

- 정답이 결정적 필터의 출력과 같게 정의돼 있어 규칙 비교군은 틀릴 수 없다. 이 데이터로는 "모델이
  규칙보다 나은가"를 잴 수 없다.
- 합성 번들이다. 실제 `aic diagnose` 증거는 섹션이 더 많고 길며, 기존 redaction이 호스트명·경로·저널
  본문을 남긴다. Jev 64k 문맥 한도와 전송 정책은 실제 증거로 확인하지 않았다.
- LLM 입력 토큰은 `send()` 경로가 사용량을 기록하지 않아 재지 못했다.
- Jev는 ai-mesh 프록시(`JEV_ENDPOINT`) 경유로 호출했다. 1라운드는 TypeSafe 직접 호출이었고 p50이
  246ms였다(이번 288ms). 모델 별칭은 `jev-latest`이며 응답의 `model`은 `jev-1.13.0`이었다.

# production 반영 (2026-09-22)

2라운드 결론대로 모델을 쓰지 않고 결정적 규칙을 `aic diagnose`에 넣었다. 목적은 정확도가 아니라
비용과 지연이다.

## 무엇이 바뀌었나

- `scan_findings`가 `docker_ps`·`k8s_pods_notready`·`k8s_crashloop_pods`·`k8s_nodes`도 본다. 이전에는
  이 네 섹션에서 발견이 하나도 나오지 않았다.
- 발견마다 후속 확인 대상을 단다. 이전에는 섹션 하나에 대상 하나여서 fd 누수 프로세스가 셋이어도
  첫 번째만 붙었고, `failed_units` 말고는 아예 붙지 않았다.
- `proc_fd_top`을 process 범주에 넣었다. 이전에는 auto-RCA 경로에만 있어 `aic diagnose`에서
  `proc_fd <pid>` 후속 확인이 나올 수 없었다. 호스트 전역 합계인 `fd`만 수집되는데, 그 값으로는
  프로세스 하나의 누수가 묻힌다(`probes.rs`의 실측 주석 참고).
- `--follow-up`은 결정적 제안이 있으면 그것을 먼저 실행하고 분석을 한 번만 한다. 지목된 대상이
  없을 때만 LLM에게 무엇을 더 볼지 묻고 재분석한다. 게이트와 상한은 제안 출처와 무관하게 같다 —
  제안자가 누구냐로 권한이 달라지면 게이트의 의미가 없다.
- `send` 경로가 토큰 사용량을 기록한다. 이전에는 `send_messages`만 기록해서 `aic`가 자기 LLM 비용을
  알지 못했다. 진단은 호출 수·입출력 토큰·소요 시간·제안 출처를 audit에 남긴다.

## 실측 — 같은 호스트(macOS), 같은 provider(ai-mesh/luna)

| 경로 | LLM 호출 | 입력 토큰 | 출력 토큰 | 소요 |
|---|---|---|---|---|
| 스캐너가 대상을 지목(`followup_source=scanner`) | 1 | 6,616 | 1,410 | 11.4초 |
| 지목 없음(`followup_source=llm`, 기존 경로) | 2 | 13,614 | 2,400 | 37.8초 |

두 번째 줄은 변경 전 기준선(2회 / 13,843 토큰 / 55.0초)과 같은 경로다. 첫 줄은 헬스체크만 실패하는
일회용 컨테이너를 띄워 잰 값이다.

**절감은 조건부다.** 스캐너가 대상을 지목할 때만 호출이 1회로 줄고, 그 외에는 기존 2회 경로가
남는다. 예를 들어 디스크 사용률 발견에는 붙일 인자가 없어 여전히 LLM이 다음 probe를 고른다. 어느
경로였는지는 audit의 `followup_source`로 가른다.

## 실제 출력에서 찾은 결함

합성 데이터로만 검증했을 때는 보이지 않았다. 실제 `aic diagnose --json` 출력으로 돌려 보고 찾았다.

- **redaction이 `docker ps` 열 정렬을 깨뜨린다.** 스캐너의 입력은 redaction을 거친 스냅샷인데,
  PORTS의 IPv4가 `[REDACTED:ipv4]`로 길어지면서 NAMES·SIZE 열이 행마다 다른 만큼 오른쪽으로
  밀린다(실측: 같은 표에서 +8과 +16이 섞였다). docker는 원본 폭으로 패딩을 끝낸 뒤라 헤더 위치가
  더는 데이터 위치가 아니다. 헤더 오프셋으로 자르면 이름이 잘려 게이트에서 거부되고 STATUS 칸이
  어긋나 정상 컨테이너가 문제로 잡힌다. SIZE의 `(virtual` 앞앞 토큰과 STATUS의 고정 낱말을 앵커로
  바꿨고, 실제 줄을 그대로 쓴 회귀 테스트로 고정했다.
- **`docker ps`는 `-s`로 돈다.** NAMES 뒤에 SIZE 열이 있어 마지막 토큰이 이름이 아니다. 1라운드
  합성 표는 `--format table`을 가정해 NAMES가 마지막이었다.
- **`kubectl`은 클러스터가 없어도 exit 0이다.** stdout이 비고 오류는 stderr로 간다. stdout만 읽으므로
  없는 pod을 대상으로 삼지 않는다.

## 남은 것

- `docker ps` 행 파서가 production(`diagnose.rs`)과 실험 하네스(`eval/src/followup.rs`) 두 곳에 있다.
  쓰임이 달라 합치지 않았다 — production은 대상 하나를 고르고 하네스는 템플릿별 후보 목록을 만든다.
  양쪽 모두 같은 실제 줄로 회귀 테스트를 건다.
- 결정적 제안은 스캐너가 있는 섹션에서만 나온다. 나머지 약 50개 probe는 여전히 LLM 경로다.
- 절감 폭은 호스트 한 대에서 각 경로 한 번씩 잰 값이다. 여러 호스트·증상에서의 분포는 audit이
  쌓이면 다시 본다.
