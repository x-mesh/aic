# Error Cause Classification Evaluation

> 명령 실패 출력에서 **원인 계열**을 고르는 일을 규칙·TypeSafe Jev·LLM으로 비교한 결과.
> 실행 상세와 원시 수치는 `eval/RESULTS.md`의 "원인 범주 분류" 절.
> 작성일: 2026-09-23 · 상태: 1라운드 완료, production 반영 · 결론: **규칙이 일반화하지 못한다. 모델이 필요하다.**

## 왜 이 시험을 했나

앞선 세 시험에서 Jev는 한 번도 채택되지 않았다.

| 시험 | 결과 |
|---|---|
| 증상 → 진단 범주 | 규칙 어휘를 넓히자 Jev와 통계적으로 구별되지 않음 → 규칙 채택 |
| probe 출력 판정 | 스캐너 대비 정밀도 0.750 < 중단선 0.85 → 보류 |
| follow-up probe 선택 | 후보를 좁히니 규칙이 1.000 → 규칙 채택 |

세 번 다 졌지만, 세 번 다 **입력이 형식이 안정적인 표**였다. `failed_units`·`docker ps`·
`kubectl get pods`·`proc_fd_top`은 파싱하면 답이 나온다. 형식이 있는 곳에서 결정적 규칙이 이기는
것은 당연하고, 실제로 그랬다. Jev의 주장이 참인지 가리려면 **규칙이 원리적으로 못 가는 입력**이
필요했다.

명령 실패 출력이 그것이다. 형식이 없고, 도구마다 어휘가 다르고, 로케일에 따라 문장까지 바뀐다.

## 무엇을 쟀나

`aic analyze`는 명령 실패를 설명한다. `error_analyzer::deterministic_known_error`가 다섯 가지를
결정적으로 잡고(command not found, permission denied, 포트 점유, git non-fast-forward, docker
daemon), **나머지는 전부 LLM으로 간다.** 이 시험의 모수는 그 나머지다.

범주 10개는 **다음 조치가 달라지는 단위**로 나눴다. 표면 어휘가 아니라 조치가 기준이다.

`not_found` · `usage` · `malformed_input` · `network` · `tls` · `auth` · `remote_error` ·
`state` · `dependency` · `resource`

데이터는 실제로 실행해 받은 실패 출력이다. 부작용 없는 읽기 전용 명령만 골랐고, 네트워크는 닫힌
로컬 포트와 절대 해석되지 않는 `.invalid` 호스트(RFC 2606), 공개 테스트 엔드포인트만 썼다. 개인
경로만 일반화했고 형식은 그대로 두었다. 사용자의 터미널 히스토리는 쓰지 않았다.

## 방법론 — 이번에 고친 것

2라운드에서 규칙 어휘를 시험 집합에 맞춰 넓힌 뒤 "규칙이 모델을 따라잡았다"고 결론 냈다. 그 결론이
과적합이었을 수 있어 이번에는 규칙을 쓰는 데이터와 재는 데이터를 분리했다.

- **개발 분할 105건** — 출력을 전부 읽고 규칙 키워드·Jev 지시문·LLM 프롬프트를 맞췄다.
- **최종 분할 64건** — 명령을 고를 때 **의도한 범주**로만 라벨을 달고 출력은 읽지 않았다. 검증은
  기계적으로만 했다(결정적 테이블에 걸리는지, 출력이 비었는지). 74건 중 9건이 그렇게 걸러졌다.
- 최종 분할을 본 뒤에는 어느 비교군도 조정하지 않았다.

## 결과

### 개발 분할 105건 — 규칙에 유리한 쪽

| 비교군 | 정확도 | top-3 | 기권 | p50 | p95 |
|---|---|---|---|---|---|
| jev | 0.981 | 1.000 | 0.000 | 249ms | 389ms |
| llm | 0.952 | 0.952 | 0.000 | 1,076ms | 2,988ms |
| rules | 0.952 | 0.952 | 0.038 | 0ms | 0ms |

### 최종 분할 64건 — 출력을 보지 않고 라벨한 데이터

| 비교군 | 정확도 | top-3 | 기권 | 반복 일치율 | p50 | p95 | 입력 토큰(64건) |
|---|---|---|---|---|---|---|---|
| jev | **0.906** | 0.969 | 0.000 | 1.000 | 246ms | 441ms | 61,464 (호출당 960) |
| llm | **0.922** | 0.922 | 0.000 | 1.000 | 890ms | 2,724ms | 49,834 (호출당 778) |
| rules | **0.672** | 0.672 | 0.250 | 1.000 | 0ms | 0ms | 0 |

**규칙이 0.952에서 0.672로 떨어졌다.** 28%p다. 과적합 의심이 사실이었고, 그 크기가 이 정도다.
두 모델은 유지됐다(jev 0.981→0.906, llm 0.952→0.922).

### 짝지은 비교 (같은 사례, 1회차)

| 비교 | 앞만 맞음 | 뒤만 맞음 | 둘 다 | 부호검정 |
|---|---|---|---|---|
| jev vs rules | 16 | 1 | 42 | p = 0.00027 |
| llm vs rules | 17 | 1 | 42 | p = 0.00014 |
| jev vs llm | 0 | 1 | 58 | p = 1.0 |

모델과 규칙의 차이는 유의하고, **Jev와 LLM의 차이는 없다**(불일치 1쌍).

## 규칙은 어디서 무너졌나

기권이 16건(25%)이다. 어느 키워드에도 걸리지 않아 답을 내지 못했다. 정답 범주는
`malformed_input` 6, `not_found` 3, `usage` 3, `network` 2, `state` 2로 고르게 퍼져 있다. 특정
계열이 약한 것이 아니라 **처음 보는 어휘에 전부 약하다.**

범주별로는 `malformed_input` 4/11, `state` 3/7, `usage` 8/11에서 갈렸다. 같은 실패를 도구마다 다른
말로 하기 때문이다. 개발 분할에서는 `parse error`·`syntaxerror`·`unrecognized archive format`을
넣어 11/16을 맞췄지만, 최종 분할의 `invalid argument`·`End-of-central-directory`·`no configuration
file provided` 같은 표현은 목록에 없었다. 키워드를 더 넣으면 이 64건은 맞히겠지만 그것이 바로
2라운드에서 한 일이고, 다음 64건에서 또 무너진다.

## 모델이 틀린 곳

셋 다 틀린 사례는 4건인데, **그중 3건은 제 라벨이 틀렸다.** 최종 분할을 출력을 보지 않고 라벨한
대가이며, 예상했던 위험이다.

| 명령 | 실제 출력 | 사전 라벨 | 실제 원인 |
|---|---|---|---|
| `docker push absent-registry.invalid/x:1` | `An image does not exist locally with the tag` | auth/network | **not_found** — 네트워크에 닿기 전에 로컬 이미지가 없어 실패 |
| `base64 -d a.json` | `invalid argument a.json` + usage | malformed_input | **usage** — macOS `base64`는 `-i`가 필요 |
| `npx tsc --noEmit a.ts` | `npm error could not determine executable to run` | malformed_input | **dependency/usage** — 타입 오류에 닿기 전에 실행 파일을 못 찾음 |

라벨 오류는 세 비교군에 똑같이 적용되므로 **비교는 유효하다.** 다만 절대 정확도는 낮게 나왔다.
사후로 세 라벨을 고치면 jev 0.953, llm 0.969, rules 0.703이 된다. 결론은 바뀌지 않는다.

라벨이 맞는데 틀린 것은 `docker compose ps`의 `no configuration file provided: not found` 하나다.
글자는 "not found"지만 조치는 "compose 파일이 있는 디렉터리로 가라"이므로 `state`다. 세 비교군 모두
글자를 따라갔다.

Jev와 LLM이 갈린 유일한 사례는 `nslookup absent-host.invalid`의 `server can't find ...: NXDOMAIN`
이다. Jev는 `not_found`, LLM은 `network`를 골랐다. 이름이 없는 것은 맞지만 조치는 DNS 확인이므로
LLM이 맞다.

## 결론

**이 자리에서는 모델이 필요하다.** 형식 없는 텍스트에서 원인을 가리는 일은 키워드로 일반화되지
않는다는 것이 처음으로 수치로 나왔고(0.952 → 0.672), 두 모델은 유지됐다.

**Jev와 LLM 중에서는 Jev다.** 정확도가 통계적으로 같고(불일치 1쌍), 지연이 3.6배 짧으며(246ms 대
890ms), 비용이 64회에 0.0026달러다. 반복 일치율은 둘 다 1.000이다. 비생성형이라 선택지 밖 값이
나올 수 없다는 것도 이 용도에서는 이점이다 — 이번 실행에서 형식 위반은 0건이었다.

지연 차이는 이 프롬프트가 작아서 3.6배에 그친다. 진단 경로처럼 증거가 길어지면 LLM 쪽만 커진다.

## 남은 제한

- 최종 n=64는 작다. `resource` 2건, `tls` 3건, `remote_error` 3건처럼 얇은 범주의 수치는 신뢰할 수
  없다. 부호검정은 짝지은 불일치 쌍에만 의존하므로 이 한계에 덜 민감하지만, 범주별 표는 참고값이다.
- 실패는 한 대의 macOS 호스트에서 만들었다. Linux의 같은 도구가 다른 문구를 내므로 그쪽 일반화는
  확인하지 않았다. 한국어 메시지가 섞인 것은 이 호스트의 로케일 덕분이고, 개발 분할에서 LLM이 9건 중
  6건만 맞힌 반면 Jev는 9/9였다(TypeSafe 문서의 CJK 경고와 반대 방향이지만 n이 작다).
- 라벨은 제가 매겼다. 최종 분할은 출력을 보지 않아 편향을 줄였지만, 그 대신 라벨 오류가 3건 생겼다.
- LLM 비용은 provider 단가를 확인하지 못해 토큰만 적었다.

## 다음 단계

1. 이 결과를 근거로 `aic analyze`에 배선한다: 결정적 테이블에서 걸리지 않은 실패에 Jev로 원인
   범주를 붙인다. 범주별 조치 템플릿을 주거나, LLM 설명 프롬프트에 범주를 실어 보내 답을 좁힌다.
   어느 쪽이든 게이트는 필요하다 — 범주가 틀려도 사용자가 알아볼 수 있어야 한다.
2. Linux 호스트에서 같은 명령 집합을 돌려 문구 차이에 대한 일반화를 확인한다.
3. 얇은 범주(`resource`·`tls`·`remote_error`)를 채워 범주별 수치를 신뢰 가능하게 만든다.

# production 반영 (2026-09-23)

## 무엇이 붙었나

`aic`가 실패를 분석할 때, 결정적 테이블이 잡지 못한 경우에만 원인 계열을 먼저 분류한다. 순서는
결정적 테이블 → recipe → 캐시 → **분류** → LLM 설명이다. 앞의 셋에서 답이 나오면 분류는 돌지
않는다 — 분류는 LLM 호출에 붙는 것이지 매 실패에 붙는 것이 아니다.

- 설정 `[jev]`는 **기본 비활성**이다. 켜면 명령과 종료 코드와 정리된 출력이 분류 서비스로 나가므로
  명시적 opt-in을 유지한다. 키는 `api_key`(평문 또는 `keychain:` 참조)이고, 없으면 `JEV_API_KEY`
  환경변수를 본다.
- 분류가 붙으면 `추정 원인 계열: <범주> (<confidence>)` 한 줄을 먼저 보여준다. **추정**이라고 쓰는
  이유는 측정 정확도가 0.906이기 때문이다.
- 설명 프롬프트에는 힌트로만 실린다. "분류기가 이렇게 봤다. 출발 가설로 쓰되 출력과 어긋나면
  무시하라"는 문구를 함께 넣는다. 단정으로 실으면 열 번에 한 번 틀린 전제 위에 설명을 쓴다.
- 결과는 audit에 `error_cause_classified`(범주·confidence·종료 코드·소요)로 남는다.
- 미설정·키 없음·오류·시간 초과(기본 5초)는 전부 조용히 건너뛴다. 분류는 부가 정보이지 분석의
  전제가 아니므로, 외부 서비스가 죽었다고 로컬 분석까지 막으면 안 된다.

## 실측 (같은 macOS 호스트, ai-mesh 경유)

| 명령 | 분류 | confidence | 분류 소요 | 이어진 LLM |
|---|---|---|---|---|
| `curl https://expired.badssl.com/` | tls | 0.99 | 457ms | 3,721ms |
| `git stash pop` | state | 0.90 | 1,349ms | — |
| `python3 -c "import absent_module_zzz"` | dependency | 0.91 | 460ms | — |

셋 다 실험에서 쓴 라벨과 같다. 프록시 경유라 실험의 p50 246ms보다 느리고, 첫 호출은 연결 수립이
포함돼 더 길다.

## 지금은 비용을 줄이지 않는다

분류는 LLM 호출을 **대체하지 않고 덧붙인다.** 진단 경로에서 한 것(결정적 follow-up으로 호출을
2회에서 1회로)과 다르다. 이유는 근거가 없어서다 — 범주만으로 쓴 설명이 LLM 설명만큼 쓸모 있는지
재지 않았다. `error_cause_classified`가 쌓이면 어느 범주가 얼마나 나오는지 알게 되고, 그때 범주별
템플릿으로 LLM을 건너뛸지 정한다. 측정 없이 먼저 끄면 그것이 바로 이 프로젝트가 세 번 피한 실수다.
