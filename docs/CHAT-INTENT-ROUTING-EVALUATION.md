# Chat Intent Routing Evaluation

> `aic chat`에 슬래시 없이 들어온 입력을 네 처리 경로 중 하나로 보내는 판정을 규칙·TypeSafe Jev·LLM으로
> 비교한 결과. 원시 수치와 재현 방법은 `eval/RESULTS.md`의 "채팅 의도 라우팅" 절.
> 작성일: 2026-09-23 · 상태: 1라운드 완료 · 결론: **규칙은 일반화하지 못한다. Jev가 LLM과 같은 정확도로 3.6배 빠르다.** 배선 전에 라우팅 자체의 절감을 재야 한다.

## 왜 이 시험을 했나

슬래시 없이 쓴 채팅 입력은 도구 호출 루프(`run_turn`)로 간다. 그 루프에서 LLM은 셸 명령을 직접
지어내고, 반복할 때마다 history 전체를 다시 보낸다. 같은 요청을 `/diagnose` 뒤에 쓰면 probe
카탈로그에서 결정적으로 모으고 LLM을 한 번(follow-up이 있으면 최대 두 번) 부른다. 진단성 요청을 알아볼
수 있으면 싼 경로로 보낼 수 있다.

입력은 사람이 쓴 자유 문장이고 출력은 네 개짜리 닫힌 집합이다. 원인 범주 실험에서 Jev가 이긴 조건
(형식 없는 입력 + 닫힌 선택지)과 같다. 다만 증상→범주 실험에서는 규칙이 버텼으므로 결과를 미리 알 수
없었다.

## 경로

| 경로 | 기준 |
|---|---|
| `diagnose` | 문제를 호소하거나 원인을 찾아 달라는 요청("서버가 느려졌어") |
| `local` | 문제 호소 없이 지금 상태를 보여 달라는 요청("메모리 사용량 보여줘") |
| `explain_last` | 방금 실행한 명령의 결과·실패를 설명해 달라는 요청("방금 에러 뭐야") |
| `agent` | 그 외(파일·코드·설정, 작업 요청, 개념 설명, 인사) |

## 방법

- **개발 분할 107건** — 제가 썼다. 경계 사례 4건("디스크 꽉 찼는지 확인해줘"는 `local`과 `diagnose`
  모두 타당)과 규칙 함정 4건("디스크 정리하는 스크립트 만들어줘"는 증상 낱말이 있지만 작업 요청)을
  넣었다. 규칙은 이 분할만 보고 썼다.
- **최종 분할 120건** — `claude-sonnet-5`가 경로마다 30건씩 만들었고 저는 측정 전까지 읽지 않았다.
  LLM 비교군(`gpt-5.6-luna`)과 다른 모델을 써서 두 편향을 막았다: 규칙 작성자가 평가 문장을 쓰면
  문장이 규칙 어휘를 닮고, 분류할 모델이 직접 쓴 문장을 채점하면 그 모델이 유리하다. 검증기는 생성
  모델이 만들지 않은 최종 사례를 거부한다.
- Jev와 LLM은 같은 지시문과 같은 경로 설명을 받는다.

## 결과

### 최종 분할 120건 (블라인드)

| 비교군 | 정확도 | 반복 일치율 | p50 | p95 | 입력 토큰 |
|---|---|---|---|---|---|
| jev | **0.992** | 1.000 | 238ms | 351ms | 77,774 (호출당 648, 약 $0.0033) |
| llm | **0.983** | 0.983 | 863ms | 1,959ms | 59,696 |
| rules | **0.717** | 1.000 | 0ms | 0ms | 0 |

### 개발 분할 107건 (규칙을 쓴 데이터)

| 비교군 | 정확도 | p50 |
|---|---|---|
| jev | 0.972 | 248ms |
| llm | 0.944 | 859ms |
| rules | 0.925 | 0ms |

**규칙이 0.925에서 0.717로 떨어졌다.** 원인 범주 실험(0.952 → 0.672)과 같은 모양이다. 두 모델은
오히려 올랐는데, 최종 분할에는 개발 분할에 넣은 경계 사례와 함정이 없어서다.

### 짝지은 비교 (1회차)

| 비교 | 앞만 맞음 | 뒤만 맞음 | 둘 다 | 부호검정 |
|---|---|---|---|---|
| jev vs rules | 34 | 1 | 85 | p = 2.1e-9 |
| llm vs rules | 34 | 2 | 84 | p = 1.9e-8 |
| jev vs llm | 2 | 1 | 117 | p = 1.0 |

### 경로별

| 경로 | jev | llm | rules |
|---|---|---|---|
| diagnose | 30/30 | 30/30 | **18/30** |
| explain_last | 30/30 | 28/30 | 21/30 |
| local | 29/30 | 30/30 | 19/30 |
| agent | 30/30 | 30/30 | 28/30 |

**라우팅 비용과 직결되는 `diagnose` 정밀도**(diagnose로 보낸 것 중 진짜 진단 요청): jev 30/30,
llm 30/31, rules 18/18.

## 규칙은 어떻게 무너졌나

규칙은 모르는 문장을 `agent`로 둔다. 모르는 것을 진단으로 보내면 쓸데없이 probe가 돌지만 `agent`로
두면 지금과 같은 동작이라서다. 그 결과 규칙은 57건을 `agent`로 보냈고 그중 29건이 틀렸다. 해가 되는
오라우팅은 거의 없지만(diagnose 정밀도 18/18), **진단 요청 30건 중 12건을 놓쳐 절감 기회를 잃는다.**
키워드가 개발 분할의 어휘를 벗어나지 못한 것이다.

## 모델이 틀린 곳

측정 뒤에 오답 사례를 읽었다. 라벨 오류는 없었다.

| 문장 | 정답 | jev | llm |
|---|---|---|---|
| `docker stats 결과 지금 상태로` | local | explain_last (0.50) | local |
| `위에 뜬 이 메시지 무슨 뜻인지 설명해줘 ㅋㅋ` | explain_last | explain_last | agent |
| `이 에러 메시지 뭔 뜻이야?` | explain_last | explain_last | diagnose |

Jev의 유일한 오답은 "결과"라는 낱말이 직전 출력을 가리키는 것처럼 읽힌 경우이고, confidence가 0.50으로
낮았다.

## 결론

**이 자리에서는 모델이 필요하고, Jev와 LLM 중에서는 Jev다.** 정확도는 구별되지 않고(불일치 3쌍),
Jev가 3.6배 빠르며(238ms 대 863ms) 반복 일치율도 높다(1.000 대 0.983). 규칙은 개발 분할 밖에서
21%p 떨어졌다.

두 번째 채택 후보다. 원인 범주와 합쳐 보면 패턴이 분명하다 — **형식 없는 입력에서 닫힌 선택지를
고르는 일은 규칙이 일반화하지 못하고, Jev가 LLM을 싸고 빠르게 대신한다.** 형식이 있는 입력(표, 스캐너
출력)에서는 규칙이 이겼다.

## 남은 제한 — 배선 전에 확인할 것

- **라우팅의 절감을 재지 않았다.** 이 실험은 분류 정확도만 쟀다. 진단 요청을 도구 루프 대신
  `/diagnose`로 보냈을 때 토큰·지연·답의 품질이 실제로 얼마나 달라지는지는 모른다. 채팅 턴은 이제
  토큰이 기록되므로(`send_messages` 경로) 같은 요청을 두 경로로 돌려 비교할 수 있다.
- **생성 문장은 실제 문장보다 깨끗하다.** 생성 요청에 "요청 자체는 분명히 이 의도여야 한다"를 넣었으므로
  경계 사례가 적다. 두 모델이 0.98을 넘은 것도 그 때문으로 보인다. 경계 사례가 있는 개발 분할에서는
  jev 0.972, llm 0.944였다.
- **영어가 적다.** 30%를 요청했지만 생성 모델은 7건(6%)만 냈다.
- 생성 모델이 한 종류다. 다른 모델이 쓴 문장에서도 같은지는 확인하지 않았다.
- 자동 전환인지 제안("`/diagnose`로 볼까요?")인지는 제품 결정이다. 오라우팅의 비용이 절감보다 클 수
  있으므로 처음에는 제안이 안전하다.
